# Реализация ядра бизнес-логики (Расчеты и алгоритмы)

Второе задание блока 05.10.2026. Python и PostgreSQL, база practice_051026
из первого задания. Алгоритмы скидки и материалов независимы друг от друга.

## Файлы

- discount.py — чистая функция calculate_partner_discount(total_quantity).
- partner_service.py — get_partner_with_discount(connection, partner_id):
  LEFT JOIN, SUM(quantity) за весь период, COALESCE для партнёров без продаж.
  Возвращает словарь с данными партнёра, total_quantity и discount_percent;
  для отсутствующего партнёра — None.
- material_calculator.py — MaterialCalculator(connection) с методом
  calculate_materials(product_type_id, material_type_id, quantity, param_1, param_2).
- reference_schema.sql — два справочника PostgreSQL с ограничениями.
- reference_data.sql — явно учебные коэффициенты и проценты брака.
- database.py, database.ini — подключение без сохранения пароля.
- run_demo.py — демонстрация на реальной БД.
- run_tests.py, tests/ — автономные и интеграционные тесты.
- runtime.py — выбор существующего окружения .venv в корне проекта.

## Расчёты

Скидка: менее 10 000 шт. — 0%; от 10 000 — 5%;
от 50 000 — 10%; от 300 000 — 15%.
Партнёр без продаж получает total_quantity = 0 и discount_percent = 0.
Отрицательное, дробное или нечисловое количество в чистой функции скидки
вызывает ValueError; сервис получает целую неотрицательную сумму из БД.

Использована формула из задания, подтверждённая после его первоначальной отправки:

```text
ceil(param_1 × param_2 × coefficient × quantity × (1 + defect_percent / 100))
```

Процент 5 хранится как 5, а не 0.05.
Пример: ceil(2 × 3 × 1.5 × 10 × 1.05) = ceil(94.5) = 95.
Fraction сохраняет точность десятичных входных значений перед округлением вверх.

Метод каждый раз читает коэффициент и процент брака из БД одним
параметризованным запросом. ID типов не являются ID товаров из products:
это отдельные справочники. Значения от заказчика не предоставлены, поэтому
reference_data.sql содержит учебные данные. Они не выдаются за реальные нормы производства.
Повторная демонстрация сохраняет существующие значения справочников.

Несуществующие ID, отрицательные и нулевые размеры, количество <= 0,
дробное количество, bool, строки, NaN и бесконечность дают строго -1.
Ошибки запроса к справочникам также дают -1 и запись типа ошибки в консоли.
При открытой транзакции используется savepoint, чтобы ошибка не прервала
дальнейшую работу вызывающего кода. Ошибки чтения партнёра обрабатывает вызывающий код;
run_demo.py выводит инструкцию по проверке подключения.

## Запуск в VS Code без командной строки

1. Откройте корневую папку hexlet.
2. Если ещё не импортировали данные: запустите run_import.py в соседней папке
   «Инфраструктура данных и ETL (База данных в 3NF)».
3. Проверьте database.ini в этой папке: localhost, 5432, practice_051026, postgres.
4. Откройте run_demo.py и нажмите Run Python File.
5. Введите пароль PostgreSQL в терминале VS Code. Символы пароля не отображаются.
6. Скрипт создаст недостающие справочники, добавит учебные значения и покажет
   скидки пяти партнёров: объёмы 2, 1, 3, 10 и 1 шт.; скидки всех — 0%.
   При исходных справочниках результат расчёта сырья — 95, ошибочных примеров — -1.

Рабочие партнёры, товары и продажи демонстрацией не изменяются.
Справочники можно также создать вручную в Query Tool базы practice_051026:
сначала reference_schema.sql, затем reference_data.sql.
Основной run_app.py пока запускает CRM предыдущего блока.

Если .venv отсутствует, в VS Code выберите Python: Create Environment → Venv
и requirements.txt этой папки для установки зависимостей.

## Проверка

Откройте run_tests.py и нажмите Run Python File. Автономные тесты работают без БД.
Проверяются границы скидок, округление, брак, неверные параметры, отсутствие ID
и ошибки СУБД. Проверки PostgreSQL пропускаются, если не задан TEST_DATABASE_DSN.

Для полного прогона в PowerShell из этой папки, используя интерпретатор .venv:

```powershell
$env:TEST_DATABASE_DSN = 'host=localhost port=5432 dbname=practice_051026 user=postgres'
python run_tests.py
```

Пароль для интеграционных тестов передайте через PGPASSWORD в своей среде либо pgpass.
Не сохраняйте пароль в файлах проекта. Пользователю БД нужно право CREATE.
Каждый тест создаёт собственную схему business_test_<uuid>, затем удаляет её;
рабочие таблицы public не затрагиваются.

Проверено 11.10.2026: 60 тестов прошли (55 автономных и 5 интеграционных).
Результат — test_results.txt, вывод демонстрации — demo_result.txt.
Проверка выполнена на отдельном PostgreSQL 18 (127.0.0.1:55439), Python 3.14.
Для запуска на вашем сервере localhost:5432 выполните run_demo.py с вашим паролем.
